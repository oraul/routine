# Design: a render must be fresh

## The queued design was refuted before it was proposed

`BACKLOG.md` carried this as "the freshness gate", designed and
blocked: *"`routine-release-check` regenerates every render in the
bundle being cut and compares byte for byte"*, blocked on the
per-release evidence directory.

Both halves were wrong, and P0 measured why.

**It is not blocked on the evidence directory.** The render that is
actually stale — `evidence/retro.txt` — exists today, carries a
generator header today, and shipped stale in three releases. Waiting
for a per-release directory to check renders that already exist is a
dependency invented by the design, not by the defect.

**It cannot regenerate-and-compare inside the release path as
stated.** `routine-release-check` is the `release` workflow's Gate
step, running on `actions/checkout` of `main`. `runs/` is gitignored,
so that checkout has no corpus. Measured on a clean `git archive` of
HEAD, which is what CI gets:

```
$ bin/routine-evidence
# generated by bin/routine-evidence at 2026-08-27T17:47:14Z
...
routine-retro: no telemetry found under <checkout>/runs
```

A gate comparing that against the committed render would refuse every
release the workflow has ever published. The premise "the release
regenerates its renders" is false wherever the release actually runs.

`bin/routine-evidence` had already written this down in its own header:
*"Freshness is not claimed — runs/ is absent in CI, so no check can
prove this current."* The queued design contradicted a boundary stated
in the code it was about to gate.

## What the check therefore is

A render is decided where its corpus exists, and openly undecided
where it does not. Three consequences:

- **The corpus-less case exits 0 and says so.** Refusing blocks every
  published release; passing in silence reports a judgment never made.
  Printing "not decided" and exiting 0 is the only option that is both
  operable and honest, and it matches the posture `routine-record-lint`
  already takes toward a range it cannot establish.
- **This makes the gate weaker than it reads.** It fires on the
  driver's local run, never on the workflow's. That is not a
  compromise smuggled in: it is the whole guarantee, so the spec says
  it in its own requirement rather than in a footnote. The gate still
  binds the machine where staleness is committed, which is the only
  machine that can commit it.
- **It would have caught this defect.** `routine-release-check v0.14.0`
  ran locally, on this machine, with the corpus present, and blessed a
  render 13 days stale. That run is the evidence the placement is
  right.

## Details that decide correctness

- **The timestamp line is excluded from the comparison.** The header
  carries the generation time, so a byte-for-byte comparison including
  it refuses everything, always. Excluding exactly that line and
  comparing the rest is the difference between a gate and a tripwire.
  Measured: with the line excluded, the committed render still
  disagrees on 47 lines, so exclusion loses nothing real.
- **Renders are found by header, not by filename.** The header already
  names the generator, so the file describes how to check itself and a
  render added later is covered without touching this script.
- **A named generator is a code-execution path.** The header is data
  in a file; running whatever it names would let a file run any
  command. Only a repo-local `bin/routine-*` script is executed, and
  anything else is refused rather than run.
- **No auto-regeneration.** Carried unchanged from the queued design,
  which got this part right: a gate that fixes what it judges has
  judged nothing.

## Boundaries recorded rather than hidden

- A render committed on another machine legitimately differs from this
  machine's corpus. Run evidence is machine-local; regenerating before
  cutting a release is the instruction that resolves it. Earning
  condition for a rethink: multi-machine releases.
- The check decides renders only. Whether a record's lesson is true
  stays the author's, exactly as the record rule states.
- The durable fix for the CI blind spot is the corpus living in the
  repository — the queued release-evidence directory. This change does
  not pretend to be that, and the Gate entry for run evidence stays
  open.

## The spec already forbade this, and had to be amended first

The `evidence` capability stated it outright: *"Freshness SHALL NOT be
claimed mechanically: `runs/` is absent in CI, so no check can prove
the snapshot current."* Building the gate without touching that
sentence would have shipped a script contradicting a live requirement.

The sentence is right about CI and overgeneralised in its conclusion.
Amended, it says freshness is decided wherever the declared corpus is
present, not claimed where it is absent, and the timestamp remains the
honest statement in the undecidable case. The amendment carries the
requirement's live lines and declares the four it drops, which is the
second use of the removal grammar and the first that needed no hand
override.

## How the undecidable case is detected

Exit codes cannot distinguish it: measured, `routine-retro` and
`routine-evidence` both exit 0 whether or not any telemetry exists, so
"the generator failed" is not available as a signal. Nor is "the
corpus directory is missing" — `runs/routine/README.md` is tracked, so
`runs/` exists in a clean checkout while holding nothing to render.

So the render declares what it derives from, in the header it already
uses to declare its generator: a repository-relative pattern matching
the files the body came from. Zero matches means undecidable. The
check globs and counts; it knows nothing about telemetry, retros or
runs, which keeps the rule general and keeps this script out of the
business of understanding any particular render.
