# Release record: v0.9.0

Compared against v0.8.0. The range is the three merges in `v0.8.0..HEAD`; nothing outside it is credited here, and `routine-record-lint` now refuses a citation that strays.

## Caffeine

- **A record's citations are checked against the release they claim.** The claim "this release did that" is now decidable rather than trusted, and the rule was chosen by measurement rather than by taste.

  evidence: `routine-record-lint` refuses a `#NNN` that is not a merge in `<prev>..HEAD` (#90). The obvious alternative — requiring every `lives in:` path to appear in the range diff — was rejected because it fails both directions: it refuses `lib/paths.sh`, correctly cited by the v0.8.0 record though untouched that release, and it passes the bad entry, whose archived design note *was* in range. Verified end to end in the real repository, not only in fixtures.

  lives in: `bin/routine-record-lint`

- **A green-at-birth claim is proven by a script instead of asserted.** `routine-tdd red` refused a scenario that passed, so one claim was checked every time; its mirror was checked by nobody, and a false characterization only made the suite red somewhere.

  evidence: `routine-tdd characterize` requires a pass and refuses a failure (#91). Replayed against run 0005's real false characterization it yields `lib/order.rb:28:in 'total_cents'` — the line naming what raises, which that run's analyst had to derive by reading the worktree because the developer's paraphrase lost it.

  lives in: `bin/routine-tdd`, `openspec/specs/tdd/spec.md`

- **The failure text is captured by the script that already holds it.** Telling a developer to paste a failure into a defect reason is prompt-level and therefore never load-bearing; in run 0005 a careful developer paraphrased accurately and still lost the exception, message and line.

  evidence: a refused `characterize` writes both streams verbatim to the task's `characterize.log`, truncated per run, and `routine-defect` carries it into the same `defect.md` entry as the reason (#91).

  lives in: `bin/routine-tdd`, `bin/routine-defect`

- **An interface between two agents can be checked for the first time.** Every pin in this repository matched load-bearing words in a single file, so a contradiction spanning two contracts was invisible by construction — which is how three careful changes walked into it.

  evidence: the cross-contract check asserts the analyst and developer agree about the TDD phases and what evidence each records (#92). Its red was `main` as it stood, not a fixture. It also required `grep -F`: the regex form matched across `routine-tdd characterize`, because `.` is any-char, and would have passed on the broken file.

  topic: testing/tdd

- **A question only the operator can answer is no longer recorded as a settled assumption.** Roughly ten entries across runs 0005 and 0006 mixed two different kinds of claim, and the analyst itself flagged one as "a caller-visible break" once implemented.

  evidence: `## Assumptions` now holds derivations — claims citable to a path and a line — while `## Questions` holds product intent the target has no opinion on, each carrying the provisional reading the decomposition was built on so the loop never stalls (#92). Which way money rounds (3050 at 33% is 2043 or 2044) is not a hard question; it is not in the code at any depth.

  Fired in a live run rather than only in fixtures: re-grounding ticket 0006 against the corrected contracts, the same analyst that had previously inferred the rounding direction and filed it as settled moved **three** business calls out of `## Assumptions` into `## Questions`, citing the payload's context almost verbatim — "this target has no real customer or revenue to infer one from."

  lives in: `agents/analyst.md`, `openspec/specs/spec-grammar/spec.md`

- **The operator's questions reach the operator, and the proceed is earned.** They lived in `grounding.md`; the approve step showed `requirement.md` and the briefings. The one checkpoint built for the operator's judgment was the one place they were invisible.

  evidence: approve shows them, and `routine-approve` refuses a proceed leaving non-floor questions unanswered while a `- none — <why>` floor never blocks (#92). Verified across all four paths, including a ticket with no `grounding.md` at all.

  Refused on its first live encounter: ticket 0006's re-entry raised four questions and `routine-approve` exited 1, printing each with its provisional reading and writing no `ticket.approve` line. The run is parked there, which is the designed outcome rather than a failure.

  lives in: `bin/routine-approve`, `skills/routine/SKILL.md`

- **The payload's context field changed what the analyst decided to decide.** The closest thing to a controlled comparison this release produced: same analyst role, same requirement text, same target, one variable added.

  evidence: the first pass on ticket 0006 recorded the rounding direction, the fractional-percent rule and the compounding rule under `## Assumptions` as settled. The re-entry, handed a context field stating there is no real customer or revenue and to say so rather than infer, moved all three to `## Questions` (#92). One observation, so by the standard applied elsewhere here it is a fix and not yet a pattern — but the direction is measured rather than hoped.

  lives in: `skills/routine/SKILL.md`

- **The two agents catch different drifts, and neither is told which.** The developer found the contradiction between its contract and the analyst's; the analyst found the target moving underneath its own anchor.

  evidence: on ticket 0006 the developer refused on the rails contradiction it was never warned about, and the re-entering analyst independently found the stale anchor (`68c7ffb` → `430ca25`), re-verified only the two files `git diff --name-only` named, and refreshed it. They read different things, so they cover different failure surfaces — which also means a contradiction in a place neither reads has no detector at all.

  lives in: `agents/developer.md`, `agents/analyst.md`

## Gate

- **This release's own first change shipped a broken interface, and that is what got worse.** #91 gave the developer a phase and left the analyst describing the old contract, so the analyst wrote "never through routine-tdd" into three acceptance lists of ticket 0006 and the developer could satisfy neither side.

  evidence: `spec.defective exit=1` on ticket 0006's record, on its first task, hours after #91 merged. Nine tasks, 437 tests and three revert-checks did not catch a change applied to half an interface.

  script that would decide it: built here (#92), and it is honest to say it was built *after* the failure rather than before. The check's existence does not retroactively make #91 safe; it makes the fourth occurrence less likely than the third was.

- **`routine-tdd characterize` has never run in a live loop.** Every claim above about the phase rests on fixtures, one replay I constructed by hand, and reasoning. Zero executions by an actual developer in an actual ticket.

  evidence: no `tdd.characterize` event appears anywhere in `runs/`. Ticket 0006 was designed to exercise it and stopped on the contradiction before reaching a single TDD call, so `characterize.log` has also never been produced by a real developer.

  Now pre-empted twice, and the reason matters more than the count: on run 0005 a developer caught the false characterization by choosing to check by hand, and on 0006's re-entry the analyst caught it by re-grounding — both before any TDD call. A stronger analyst starves the developer's refusal rails of work.

  script that would decide it: none needed — the run decides. But the design constraint is now known: every trap so far has been **readable**, and the analyst probes the target by execution, so it finds them. Exercising `characterize` requires a falsity invisible to reading and visible only to running — ordering, accumulated state across calls, something true in isolation and false in sequence. Another readable plant will be pre-empted a third time.

- **The comparison that would settle whether the rails improved still does not exist, and I briefly believed it did.** Tickets 0002 and 0003 share a title and the same `Grounded-at` (`c8655b7`), 0002 aborted and 0003 concluded clean, which looks like a controlled pair.

  evidence: the requirement text differs — 0002 specified `Order.new(review_threshold_cents:)` and 0003 restated the intent loosely. Two variables moved, so the abort-to-clean transition still cannot be attributed to the rails. The v0.8.0 record was right to refuse the attribution and I was wrong to doubt it.

  script that would decide it: a replay of each archived requirement, held verbatim, against the current rails with the target reset to that ticket's anchor. The inputs survive for every ticket and the anchors are real commits, so this is now buildable — which it was not when v0.8.0 said so.

- **A ticket was reported done having shipped nothing, and no gate noticed.** Ticket 0001, "Order discounts", concluded — and no discount code exists in the target at any commit.

  evidence: found by the analyst grounding ticket 0006, which ruled it out as "a stale fixture, not a decision this ticket inherits" and noted its tasks named `ruby/rails` and `ruby/rspec` against a target with neither. It also predates the `Grounded-at` rule, so it carries no anchor.

  script that would decide it: the audit checks that a done task has its covering green, not that the greens changed anything. A mutation check against the target — does reverting the ticket's work redden its own tests — would decide it, and nothing here does that for a target.

- **Two of shopapp's seven commits are experimental conditions I authored.** `ad24ee0` (an empty order refuses to price itself) and `430ca25` (confirming seals the order) were written to falsify a specific characterization at a specific moment, with commit messages deliberately reading like a colleague's.

  evidence: both are mine, both landed mid-ticket after the analyst had grounded, and both are load-bearing in runs 0005 and 0006. Recorded because a later reader would otherwise take that history as organic evidence of the loop handling real change.

  script that would decide it: none, and none wanted. This is a disclosure, not a defect — the alternative is a target that never surprises the loop, which proves less.

- **A permanently red check is training in progress.** `github-advanced-security` failed on #92 with `CAPIError: 400 The requested model is not supported`, from GitHub's own Copilot review agent, evaluating no code in the diff.

  evidence: #92 was merged with that check red, and the reason is stated in its merge commit. It will be red on every future PR until GitHub fixes it, and CONTRIBUTING says red leaves a PR open.

  script that would decide it: none — this is a repository setting, not a rail. But the decision is real: either the check is disabled until it works, or every merge carries a documented override, and a board that is always partly red stops meaning anything.

- **Preflight now costs 95 seconds and rises with routine's own test count.** It gates the harness on every target ticket, so the cost scales with the wrong thing.

  evidence: `gate.preflight` across six runs — 16294, 78950, 79172, 68293, 91005, 95034 ms — while the target stayed at 38 lines. The suite grew from roughly 300 tests to 446 over the same span.

  script that would decide it: none needed, no requirement states a budget. It becomes a gate the day one does, and the trend is the argument for stating one.

- **A commit message is a claim, and it can be audited against its own diff.** I did not know the grounding could do this, and it found a hole in my work using my own justification.

  evidence: `430ca25`'s message says two incidents came from state written onto an order after it settled. The re-entering analyst verified the seal is **shallow** — an Array held in an ivar is still appendable after `confirm!` — and observed that this feature adds the first order-level state that seal does not reach, "the exact failure mode the commit's own comment attributes two incidents to." Independently re-verified: the append succeeds, and `add_item` raises `FrozenError, "order is settled"` while a direct write raises Ruby's `can't modify frozen Order`.

  script that would decide it: none. A rationale in a commit message is prose, and whether the diff delivers on it is a judgment. Recorded because it is a capability of grounding nobody specified and no test would have found.

- **A characterization can be false for two independent reasons at once, so fixing the spec is not sufficient.** Task 01's pin failed both the protocol contradiction and the target drift, and the protocol fix alone would have left the second live.

  evidence: after the contracts were corrected, the pin still asserted the order is unfrozen while the target now carries `test_confirming_seals_the_order_object_itself` asserting the opposite. The analyst's conclusion is that `routine-tdd characterize` would have refused it even post-fix.

  script that would decide it: partly built — `characterize` decides the second reason. Nothing decides that a rewind reconciled the spec but skipped re-grounding, and the analyst's contract makes re-grounding a rule rather than a gate.

- **I relayed ten of the analyst's measurements to the human as fact before checking any of them.** All ten turned out exact, which is luck rather than method.

  evidence: the rounding figures, the Float `2668.75`, the compound `972`, the two distinct `FrozenError` messages, the shallow seal, the diff scope and the suite size were all reported in my summary and only verified when the human asked how assertive the run had been. Every one held. Earlier in this same session I relayed a `415 green` figure the same way and it was wrong by three.

  script that would decide it: none, and this one is mine rather than the loop's. The rail that exists is the habit of re-running a delegate's claim before repeating it, and it was not applied here.
